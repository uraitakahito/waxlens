waxlens は固定された rule の集合を archive に対して実行し、違反 1 件につき
issue を 1 件報告します。[全 rule の表](#全-rule)は **rule 定義そのものから生成**して
いるので、コードから遅れることがありません。rule 名・severity・適合レベル・profile
ごとの上書き・spec リンクはすべて `packages/core/src/validate/` 由来です。

## 表の読み方

**適合レベル**は spec が要求する強さ(`MUST` / `SHOULD` / `MAY` / `MUST NOT`)、
**severity** は違反に対して waxlens が取る扱いで、この 2 つは必ずしも一致しません。

severity は `error` / `warning` / `info` の 3 値です。**判定に効くのは `error` だけ**で、
`valid` は `error` が 0 件かどうかだけで決まります —— `warning` と `info` は何件あっても
`valid` を覆しません。

| severity | 意味 | `valid` |
| --- | --- | --- |
| `error` | これがあると使えない(再生が壊れる / 検証が成立しない) | `false` にする |
| `warning` | 直すべきだが、それだけでは壊れない | 変えない |
| `info` | 観察の記録。良し悪しの判断を含まない | 変えない |

`MUST` / `MUST NOT` / `SHOULD` / `SHOULD NOT` / `MAY` は
[RFC 2119](https://www.ietf.org/rfc/rfc2119.txt) の意味で用います。
表に出る適合レベルは **waxlens が付けた重要度ではなく、spec 側の記述を写したもの**です。

[`datapackage/resources-complete`](#datapackage-resources-complete) は `MUST` ですが `warning` です — `resources[]`
が不完全でも、それだけで replay が壊れるわけではないからです。

ずれは例外ではありません。**22 rule のうち 5 つが対角から外れ**、corpus の 30 標本
(`spec` profile) では **44 件の issue のうち 15 件**が外れます。
2 つの軸で絞り分ける方法は
[JSON レポート](/waxlens/ja/json-report/#severity-と-conformance-は別の問いに答えます)にあります。

### severity 欄が 2 つ並ぶことがあります

**1 つの rule が、見つけたものによって別の severity を出す**ことがあります。その場合
severity 欄には出しうる値がすべて並びます。

[`datapackage/digest`](#datapackage-digest) は `warning / error` です — digest ファイルが
無いのは仕様上 `SHOULD` 未達なので `warning`、ファイルはあるのに hash が合わないのは
**アーカイブが変更された可能性**を意味するので `error`。同じ rule でも、見つけたものが
違えば扱いも違います。

該当するのは 22 rule のうち 5 つです。

**profile 上書き**は、指定した `--profile` の下で severity を組み替えます。空欄の rule は
どの profile でも rule が出したままです。**その rule の指摘が全部変わるとは限らない**ので、
複数が対象なら件数を添えています。適合レベルは profile では動きません —— spec がそう
書いている、という事実だからです。
[プロファイル](/waxlens/ja/profiles/)を参照。

:::note[出典側の事情]
明示的に RFC 2119 を宣言しているのは
[Data Package](https://uraitakahito.github.io/datapackage/ja/) だけです
（各仕様書の冒頭に「本文書のキーワードは RFC 2119 に記述されたとおりに解釈される」とある）。
**WACZ 1.1.1 / 1.2.0・wacz-auth 0.1.0・WARC 1.1 は `MUST` や `SHOULD` を使いながら、
RFC 2119 への言及がありません**（本文中に一度も現れないことを確認済み）。

そこで waxlens は、**どの仕様に由来する適合レベルでも RFC 2119 の意味で扱います**。
慣例に従った解釈であり、出典側が明示していない部分については waxlens の側の取り決めです。
:::

## rule が見ている層

- **`wacz/*`** — `ZIP file` の構造そのもの。存在しなければならないファイル /
  ディレクトリと、予約ディレクトリに異物が無いか。
- **`datapackage/*`** — `datapackage.json`。Frictionless の構造、宣言された
  `profile`、WACZ version、そして hash が実体と一致するか。
- **`cdxj/*`** — index。wabac.js がロードできるか、offset が実在の WARC record
  を指すか、filename が `archive/` 相対か。
- **`warc/*`** — WARC の内部。gzip member が独立して展開できるか、payload digest、
  recording が完結しているか。
- **`pages/*`** — `pages/pages.jsonl` の schema 適合。
- **`fuzzy/*`** — best-effort な check。単独で適合性を主張しません。

## 同じファイルを 2 つの rule が見る理由

観点が違うので意図的にそうしています。[`wacz/required-files`](#wacz-required-files) は index が
**存在するか**を assert し、[`cdxj/index-recognised-by-wabac`](#cdxj-index-recognised-by-wabac) は wabac.js が実際に
**ロードできるか**を assert します。前者を通って後者で落ちる archive はあり得て、
その区別こそが producer に問題の所在を教えます。

同様に `datapackage.json` の存在チェックは `wacz/required-files` が担うので、
[`datapackage/profile-required`](#datapackage-profile-required) は `profile` の**値**に専念できます(不在を
二重に報告しません)。

## rule を追加するとき

rule は `packages/core/src/validate/rules/` にファイルを置き、**かつ**同ディレクトリの
`index.ts` に登録して初めて有効になります。両方が必要で、登録し忘れた rule は
一度も実行されません。docs のビルドが両者の件数を突き合わせるので、
登録忘れが静かに紛れ込むことはありません。
